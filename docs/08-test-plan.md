# 테스트 및 시연 계획

회원 HTTP·JWT·권한·모델/계약·샘플·미리보기 단위 테스트를 제공한다. MySQL 제약·ORM 검증 5개도 준비했다.
MySQL 테스트는 TEST_DATABASE_URL이 없으면 건너뛴다.
회원 HTTP 테스트는 임시 SQLite users만 사용해 인증 로직을 확인하며 MySQL 무결성·잠금 검증을 대체하지 않는다.
Node.js 테스트는 토큰 전달·401 해제·업무 오류·네트워크 오류를 검증한다.
아래 항목은 업무 구현 시 추가할 인수 기준이다.
무결성과 잠금 검증은 SQLite 대체 없이 MySQL에서 수행한다.

## MySQL 제약 테스트 실행

`tests/test_database_constraints.py`는 빈 전용 DB에서 DDL·seed를 적용한 뒤
인접 구간 재판매, 중복 구간 PK, 취소 후 점유 재확보, 열차종류 FK와 실제 MySQL/ORM 컬럼·PK를 검사한다.
DB 이름은 `_test`로 끝나야 하며 기존 테이블이 있으면 삭제하지 않고 실패한다.
테스트 후 스키마가 남으므로 다음 실행에는 새 빈 테스트 DB를 준비한다.

```powershell
$env:TEST_DATABASE_URL = 'mysql+pymysql://사용자:비밀번호@127.0.0.1:3307/train_app_test?charset=utf8mb4'
.\.venv\Scripts\python.exe -m pytest tests/test_database_constraints.py -q
Remove-Item Env:TEST_DATABASE_URL
```

GitHub Actions는 일회용 MySQL 8.4 서비스를 준비해 이 검사도 실행하도록 구성했다.
이 파일을 작성한 로컬 환경에서는 MySQL이 없어 5개를 실행하지 않았다.
DB 제약 테스트는 서비스의 전체 rollback·권한·실제 동시 요청을 검증한 결과로 간주하지 않는다.

동시성 테스트는 연결 2개와 barrier를 사용해 실제 동시 요청을 만들고 최종 DB 상태도 검사한다.
시스템 시간은 주입 가능한 clock으로 고정한다. 성공 응답만 검사하지 않는다.
시연: 회원가입 → 날짜 검색 → 2좌석 예약 → 결제 → 발권 조회 → 1장 취소·환불 → 나머지 탑승 확인.
별도 시연으로 연속 구간 재판매, 좌석 충돌, 만료, 중복 결제를 확인한다.

## 컨테이너 실행 검증

CI의 `docker` 작업은 Compose 설정을 확인하고 실제 Docker 이미지를 빌드한다.
루트와 app 안에 가상 `.env` 파일을 넣어도 이미지에 포함되지 않는지, UID 10001로 실행하는지 확인한다.
`PORT=8080`으로 웹 컨테이너를 실행해 health·홈페이지·API 문서·정적 JS의 HTTP 응답을 확인한다.
MySQL 제약·ORM 검증은 별도 `python` CI가 담당하며 Render의 실제 DB 연결은 배포 환경에서 확인한다.
로컬 실행과 배포 절차는 [12-deployment.md](12-deployment.md)를 따른다.
